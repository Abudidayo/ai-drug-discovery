## 1. What exactly is this paper, and what problem does it address?

### Takeaway
This is a 16-page industrial **technical note**, posted 6 Aug 2026 as v1 under cs.AI, by 19 authors from AstraZeneca's Biological Insights Knowledge Graph (BIKG) team. It describes **"Research Assistant"**, an internal multi-agent LLM chat system. The system answers biomedical questions with citation-linked evidence drawn from literature, a knowledge graph, chemistry, clinical trials, safety and expression data. **It is not a drug-repurposing method or benchmark paper.** It contains no docking, no structure work, no repurposing evaluation and no quantitative accuracy results. What it offers the team is a set of architecture and design lessons from a production deployment.

### Inferences
- **Mismatch with what the team may have expected.** The paper does not name any of the team's planned databases (Open Targets, ChEMBL, PubChem, RCSB PDB). It has no docking or co-folding, and no repurposing benchmark. The closest analogues to the team's pipeline are:

  - the Knowledge Graph Agent, comparable to Open Targets;
  - the Discover Agent, which ensembles graph-ML link prediction with a consensus step, comparable to the team's "model jury".

It is best used to justify design choices: "a production pharma system made the same choice, for these stated reasons".

## 2. What is the pipeline and architecture, and which databases, models and tools does it use?

### Takeaway
The backend is Python (asyncio and FastAPI) built on the **Apache Burr** state-machine framework, and it streams state updates over **server-sent events** to a React/TypeScript UI. The LLM assigns **topics** to each query, and a developer-maintained topic-to-agent map picks a subset of **12 "Tool Agents"**. Each Tool Agent is a tool API plus a prompt, with **Instructor/Pydantic** structured outputs. Every agent returns the same **`Observation`** evidence object (ID, URL, data, citation string). Agents run **in parallel**, and a **larger LLM** then synthesises the answer with evidence IDs injected for grounding. The models named are **Gemini 3 Flash** and **Gemini 3.1 Pro**. A "Deep Research Mode" runs a **judge-approved, fixed-size DAG of sub-questions**. A "Discover Agent" ensembles graph ML (GCN/GAT, RotatE, ComplEx, DWPC, Sørensen similarity, PageRank) and combines the rankings with **CRank** to find the predictions where the models agree most.

### Cited Findings

#### Stack and runtime
- The backend is "written in Python with heavy use of the asyncio package", the API layer is FastAPI, and "the framework used at the heart of the application was Apache Burr". Burr is described as "a light-weight state machine framework" that supports loops and conditional execution and "offers out-of-the-box telemetry support without binding to any specific vendors". Burr Actions are Python functions that modify State. The frontend is TypeScript/React, and the backend "streams messages with state updates (using server-sent events)". — [Paper §2.1](https://arxiv.org/html/2608.12395v1#S2.SS1)
- "The system uses a parallel architecture in which a user query triggers multiple lightweight tool calls simultaneously. A final synthesis step is then performed by a larger LLM. This approach also helped keep per-query costs low." — [Paper §2.1](https://arxiv.org/html/2608.12395v1#S2.SS1)
- "Keeping the LLM instructions lean while guiding the system to rely only on the obtained external information was intended to reduce hallucinations". Also: "We believe the quality of the underlying data services and APIs contributed substantially to internal adoption." — [Paper §2.1](https://arxiv.org/html/2608.12395v1#S2.SS1)
- **Models named in the paper:**
  - Gemini 3 Flash and Gemini 3.1 Pro, which together determine the per-query cost — [Paper §2.1](https://arxiv.org/html/2608.12395v1#S2.SS1)
  - Gemini 3 Flash with Vertex AI "Grounding with Google Search", used by the Web Search Agent — [Paper §2.3.5](https://arxiv.org/html/2608.12395v1#S2.SS3.SSS5)
  - OpenAI text-embedding-3-small with ChromaDB, used by an early router that was later dropped — [Paper §2.4](https://arxiv.org/html/2608.12395v1#S2.SS4)
  - four BERT-based extraction models — [Paper §2.3.7](https://arxiv.org/html/2608.12395v1#S2.SS3.SSS7)
  - graph-ML link predictors — [Paper §2.3.6](https://arxiv.org/html/2608.12395v1#S2.SS3.SSS6)

#### Two modes
- **Scientific Mode** is a single feed-forward pass: Topic Assignment → Tool Agent Selection → Parallel Tool Agent Execution ("Evidence collected") → "Answer Synthesis with Evidence Attribution" → "Enrich response with Named Entities and Follow-up queries". Figure 2 also shows a loop: "If no data found, force Web Search agent and re-run". — [Paper §2.2](https://arxiv.org/html/2608.12395v1#S2.SS2); [Figure 2 image](https://arxiv.org/html/2608.12395v1/figure_1_export.png)
- **Deep Research Mode** works as follows:
  - The plan is "a directed acyclic graph (DAG) of questions".
  - The system "creates and revises the plan until the judge agent accepts it (with a maximal assigned number of revisions to avoid very long planning loops)".
  - The accepted DAG is topologically sorted, and each node is answered using Scientific Mode.
  - Dependent questions are rewritten with earlier answers (for example, a synonym found in a previous step).
  - Users can supply their own plan to override automatic planning.
  - "the size of the research plan is fixed at the beginning", which bounds time and budget.
  - Figure 2 summarises execution as "Execute independent sub-questions via Scientific Mode", "Resolve dependent questions iteratively", "Aggregate all the answers and data".
  - Sources: [Paper §2.2](https://arxiv.org/html/2608.12395v1#S2.SS2); [Figure 2 image](https://arxiv.org/html/2608.12395v1/figure_1_export.png)
- **Figure 3 example plan** for "What genes are associated with idiopathic pulmonary fibrosis?":
  - Q1: "What are the synonyms or popular labels for idiopathic pulmonary fibrosis?"
  - Q1 then feeds Q2: genes "genetically associated ... based on genome-wide association studies (GWAS) or clinical data".
  - Q1 also feeds Q3: "protein-coding genes frequently mutated or differentially expressed".
  - The figure is annotated: "Use answer to Q1 to re-write and answer Q2 and Q3".
  - Source: [Figure 3 image](https://arxiv.org/html/2608.12395v1/ra_plan_example.png)

#### Tool Agent contract and the evidence object
- "A Tool Agent is composed of two things: the tool API and the prompt (similar to the concept of Skills)." The prompt explains how to map free text to a structured tool query, "what are the limitations of each tool and how the returned data is formatted." — [Paper §2.3](https://arxiv.org/html/2608.12395v1#S2.SS3)
- Instructor (Pydantic validation plus retries), combined with better LLM structured output, "meant that the queries rarely fail due to model schema validation errors or malformed JSON objects." — [Paper §2.3](https://arxiv.org/html/2608.12395v1#S2.SS3)
- Every agent returns the same Pydantic `Observation` class, which contains:
  - an **ID**, "a tag used later to inject into the LLM response for grounding each statement created by the LLM";
  - a **URL** for manual inspection;
  - a **flexible data container** for sentences, tables or KG triples;
  - a **citation string** shown in the UI.
- Paper example: `id='lit-5'`, a DOI link, a single excerpt sentence, document title, journal, date, authors, `number_of_citations: 27`, `impact_factor: 6.91`. — [Paper §2.3](https://arxiv.org/html/2608.12395v1#S2.SS3)

- **Knowledge-graph guardrails.** The paper says letting an LLM write Cypher or SPARQL directly over a large graph causes three problems:
  - "Behaviour becomes non-deterministic"; for example, "genes associated with a disease" sometimes includes inferred pathway paths.
  - "Difficulty taking into account meta-level information": "one gene-disease association edge may reflect a genuine causal impact while another one only a change in expression level".
  - "Generated queries can be factually correct, but too complex and lead to timeouts."
- **The fix has four steps.** (1) Ground entities to IDs with KAZU and the BIKG mapping service, e.g. "atopic dermatitis" = "MONDO:0004980". (2) Build a prototype query over a **projected schema**. (3) Adjust it with **deterministic rules**, e.g. `r.prov IN ['OMIM_DATA', 'ORPHANET'...]`. (4) Execute it and return a summary. — [Paper §2.3.3](https://arxiv.org/html/2608.12395v1#S2.SS3.SSS3)
- **What BIKG is.** BIKG "combines relevant data for drug development from public as well as internal data sources to provide insights for a range of tasks: from identifying new targets to repurposing existing drugs". It was posted on bioRxiv on 2021-11-01 under licence cc_by_nc_nd, and the abstract does not list specific sources. — [bioRxiv API record](https://api.biorxiv.org/details/biorxiv/10.1101/2021.10.28.466262); [bioRxiv page](https://www.biorxiv.org/content/10.1101/2021.10.28.466262v1)
- **Discover Agent and consensus.** "Each model generates a ranked list of candidate links ... These rankings are then combined using CRank [18] to identify predictions with the strongest agreement across models". In Deep Research Mode "the system first generates a prediction using the Discover Agent and then retrieves evidence supporting or contradicting that relationship". The workflow "remains bounded in both runtime and token budget." — [Paper §2.3.6](https://arxiv.org/html/2608.12395v1#S2.SS3.SSS6)
- **What CRank is.** CRank is "an automatic unsupervised method for prioritizing network communities"; its code is MIT-licensed. The paper repurposes it for rank combination but does not describe how. — [mims-harvard/crank README](https://github.com/mims-harvard/crank)

#### Router ("Tool Agent Picker")
- **Version 1 (dropped).** Hand-made example questions were embedded (text-embedding-3-small, ChromaDB), and the nearest neighbour selected the agents. It was dropped for two reasons. The example set "became hard to maintain". Also, "the nearest neighbour search ... will always yield a hit, even if the query is not semantically related", and a cosine cut-off was "very hard" to define. — [Paper §2.4](https://arxiv.org/html/2608.12395v1#S2.SS4)
- **Version 2 (current).** Topic modelling over "tens of thousands of real user interactions" produced a short list of topics, such as "Chemistry Information", "Biological Relationships", "General Biomedical Knowledge", "Drug Safety" and "Recent Events". Developers map topics to agents. At runtime the LLM assigns topics, and the union of the mapped agents runs in parallel. The approach "now supports thousands of monthly interactions". "Large Language Models are good at high-level topic modeling, but they are not experts in our internal Tool Agents." — [Paper §2.4](https://arxiv.org/html/2608.12395v1#S2.SS4)
- **Why route at all.** Running all agents for every query "would lead to slower response times due to LLM endpoint limitations". Also, "limiting the amount of data fed into the context ... improves the quality of the Assistant's answers and decreases the cost of each query." — [Paper §2.4](https://arxiv.org/html/2608.12395v1#S2.SS4)

### Inferences
- **Mapping the paper onto the team's stack** (my mapping, not the paper's):
  - Compound Agent's templated GraphQL → **ChEMBL/PubChem REST calls built from fixed templates**
  - Knowledge Graph Agent with projected schema and deterministic rules → **fixed Open Targets GraphQL queries with hard-coded filters**, e.g. which evidence types count and what score thresholds apply
  - Mapping Agent → **Open Targets search / ChEMBL synonyms**, shown to students as step 1 (Figure 3 also starts with synonym resolution)
  - Clinical Trial Agent → **ClinicalTrials.gov** status lookups, used to decide whether a candidate is already being trialled
  - OFF-X → Open Targets `drugWarnings` / `adverseEvents` (see §5)
  - HPA Agent → an optional HPA "is the target expressed in the relevant tissue?" chip
  - Discover Agent plus CRank → the **model jury with rank aggregation and an agreement statistic**
  - Deep Research DAG → the team's **fixed, hand-authored pipeline DAG**, made visible in the UI
- **The paper has no multi-LLM jury.** Its "judges" are (a) a plan-acceptance judge in Deep Research Mode and (b) an offline LLM judge over logged interactions (§3). Its consensus ensemble combines *structurally different graph-ML models*, not several LLMs. Several LLMs trained on overlapping corpora probably make correlated errors, so the jury's "agreement" is weaker evidence than the paper's cross-method agreement.
- **Figure 1 overstates its evidence.** Five or more of the "28 sources" are near-duplicate web snippets (NIH, a children's hospital, UCLA Health, Cleveland Clinic, MedlinePlus) all repeating "caused by a somatic mosaic mutation in the GNAQ gene". Raw citation counts inflate apparent support. The app should count *independent evidence types and sources*, not citations.
- The figure's 38 s example also exceeds the "10 to 30 seconds" typical range given in the text. The team should design the UI for 30–60 s+ runs with streamed progress.

### Gaps
- The paper does not publish its prompts, Burr graph definitions, model parameters (temperature, thinking levels other than the web agent's "medium"), or which model runs topic assignment or the judges.
- It gives no infrastructure or hardware details and does not enumerate BIKG's sources.
- It does not explain how CRank, a community-prioritisation method, was adapted to combine link-prediction rankings.

## 3. How is it evaluated, and what are the key quantitative results?

### Takeaway
**The paper reports no evaluation numbers.** It describes four practices:
1. A 100-question **BioASQ Training 10b** yes/no subset, scored with balanced accuracy against "vanilla" LLMs such as GPT-4, used only as a sanity and regression check.
2. **STaRK**-derived overlap checks on the knowledge-graph agent.
3. An **LLM judge** run over real user interactions.
4. **User feedback**, which the paper calls the most informative signal.

It gives no scores, splits, confidence intervals, ablations, hallucination rates or citation-precision figures. Its only numbers are operational: users, cost, latency, corpus size, and one model-deployment F1 threshold.

### Cited Findings
- **BioASQ.** "we used the BioASQ Training 10b question-answer set [9]. Specifically, we used a random subset of 100 yes/no questions which allowed us to calculate balanced accuracy of the system compared to 'vanilla' LLMs, like GPT 4". It was used for the "cold start" problem and "mainly as a sanity check and for regression monitoring". **No accuracy values are given.** — [Paper §3](https://arxiv.org/html/2608.12395v1#S3)
- **Benchmarks versus real use.** "the improvements made in Research Assistant based on user feedback did not translate to performance improvements on the BioASQ question set, further exemplifying the orthogonality of biomedical QA benchmarks and real-life user requirements." Also: "The most informative evaluations came from direct user feedback". — [Paper §3](https://arxiv.org/html/2608.12395v1#S3)
- **STaRK.** STaRK's PrimeKG-based simulated queries were mapped to BIKG, and the team computed "overlap statistics between the triples returned by the Tool Agent given the input query and the expected node set" on random subsets. This was a regression monitor for the knowledge-graph agent. **No values are given.** — [Paper §3](https://arxiv.org/html/2608.12395v1#S3)
- **LLM judge.** "given a pair of real user question and a system response, would assign a score and add comments about that interaction", used to find weak areas such as missing data sources. The paper gives no judge validation or numbers. — [Paper §3](https://arxiv.org/html/2608.12395v1#S3)
- **The only figures in the paper** (quote them exactly):
  - "15,000 unique internal users within one year" — [Paper §1](https://arxiv.org/html/2608.12395v1#S1)
  - "the average cost of a Research Assistant query is only 16 cents (including all input and output tokens, using Gemini 3 Flash and Gemini 3.1 Pro models)", at "current per-token pricing by Google Cloud Platform (July 2026)" — [Paper §2.1](https://arxiv.org/html/2608.12395v1#S2.SS1)
  - "responses are typically generated within 10 to 30 seconds" — [Paper §2.1](https://arxiv.org/html/2608.12395v1#S2.SS1)
  - "over 3.8 billion sentences from over 67 million documents" — [Paper §2.3.1](https://arxiv.org/html/2608.12395v1#S2.SS3.SSS1)
  - endpoint extractors deployed "once a model reached F1 of at least 0.85" — [Paper §2.3.7](https://arxiv.org/html/2608.12395v1#S2.SS3.SSS7)
  - "thousands of monthly interactions" and "tens of thousands of real user interactions" — [Paper §2.4](https://arxiv.org/html/2608.12395v1#S2.SS4)
  - Figure 1 example: 38 s, 28 sources, 2 tools — [Figure 1 image](https://arxiv.org/html/2608.12395v1/ra_ui_manuscript.png)
- **Licences of the evaluation datasets it names:**
  - **BioASQ-QA** corpus on Zenodo: **CC-BY-2.5**, published 2022-12-19, DOI 10.5281/zenodo.7655130 — [Zenodo record](https://zenodo.org/records/7655130)
  - **STaRK** dataset: **CC-BY-4.0** — [Hugging Face dataset](https://huggingface.co/datasets/snap-stanford/stark); STaRK code: **MIT** — [GitHub](https://github.com/snap-stanford/stark)
  - **PrimeKG** repository: **MIT** — [GitHub](https://github.com/mims-harvard/PrimeKG)

### Inferences
- There is **nothing quantitative to attribute to this paper** beyond the operational figures above. Never say "the AZ paper showed X% accuracy".
- BioASQ 10b has been public since 2022, so GPT-4-era and later models may have seen it (contamination). The paper does not discuss this. More generally, public biomedical QA sets are weak evidence for LLM systems, and the paper's own "orthogonality" remark supports keeping benchmarks as regression checks only.
- The paper presents its LLM judge as a triage tool, not a validated metric. The team should do the same.
- **What transfers to a 24-hour build** is the evaluation stack, not any numbers: a tiny fixed sanity and regression set, feedback capture, and LLM-judge triage of logged runs. Concrete protocol in §5.

### Gaps
- No reported values exist for BioASQ balanced accuracy, the GPT-4 baseline, STaRK overlap or judge scores.
- The paper gives no latency distribution, per-agent ablation, cost breakdown, error taxonomy or hallucination rate.
- I did not check whether the Zenodo BioASQ-QA record contains exactly the "Training 10b" split.
- I did not check the licence of PrimeKG's data files, as opposed to its repository code.

## 4. Is there public code, data or a hosted demo? How hard is it to run or adapt in a few hours, and on what hardware?

### Takeaway
**Nothing is released**: no code, prompts, data, model weights or public demo. The system is internal to AstraZeneca and depends on proprietary services (BIKG, the CAG chemistry gateway, the NLP index, ELNs, In Vivo data, Clarivate OFF-X). It cannot be run or forked. What the team can reuse are the paper's patterns and a few permissively licensed components it names. None of them needs a GPU, because the LLM side runs on hosted APIs.

## 5. Which specific ideas would most strengthen our app, and what would judges find impressive? (Recommendations)

### Takeaway
Take the paper's **evidence-first core** and add the one thing it lacks, which quant-minded judges will probe: a **leakage-aware known-answer protocol**. The four core pieces are:
1. A typed **evidence pack** whose IDs every jury claim must cite, checked by code.
2. **Templated, deterministic data queries** instead of LLM-written GraphQL.
3. A **fixed, visible pipeline DAG** with streamed progress, cost and latency.
4. A jury modelled on the Discover Agent's consensus: independent rankings, then rank aggregation, an agreement statistic, and a "supporting versus contradicting evidence" pass.

### Cited Findings (paper patterns and live data facts these recommendations rest on)
- **Evidence IDs injected into answers** for statement-level grounding — [Paper §2.3](https://arxiv.org/html/2608.12395v1#S2.SS3)
- **Templated queries** (the CAG GraphQL templates) and **deterministic rules** over a projected knowledge-graph schema — [Paper §2.3.2](https://arxiv.org/html/2608.12395v1#S2.SS3.SSS2); [Paper §2.3.3](https://arxiv.org/html/2608.12395v1#S2.SS3.SSS3)
- **Parallel cheap tool calls with one larger synthesis model**, and an average cost of 16 cents per query — [Paper §2.1](https://arxiv.org/html/2608.12395v1#S2.SS1)
- A **bounded, fixed-size plan** checked by a judge, and evidence **supporting or contradicting** a prediction — [Paper §2.2](https://arxiv.org/html/2608.12395v1#S2.SS2); [Paper §2.3.6](https://arxiv.org/html/2608.12395v1#S2.SS3.SSS6)
- **Compositional fetching** of only the needed fields — [Paper §2.3.4](https://arxiv.org/html/2608.12395v1#S2.SS3.SSS4)
- **UI features:** entity highlighting, inline citations, a sources panel with provenance labels, a status card, example prompts, a limitations notice and thumbs feedback — [Figure 1 image](https://arxiv.org/html/2608.12395v1/ra_ui_manuscript.png)
- **LLM-judge triage of logged interactions** — [Paper §3](https://arxiv.org/html/2608.12395v1#S3)
- **Open Targets schema check (live).** The API identifies itself as "Open Targets GraphQL & REST API Beta", **apiVersion 26.9.0**, **dataVersion 26.09**.
  - The `Drug` type exposes `maximumClinicalStage`, `indications`, `mechanismsOfAction`, `drugWarnings`, `adverseEvents`, `synonyms`, `tradeNames` and `crossReferences`.
  - Indication rows (`ClinicalIndicationFromDrug`) expose `id`, `maxClinicalStage`, `disease` and `clinicalReports`.
  - The legacy fields `isApproved`, `maximumClinicalTrialPhase` and `maxPhaseForIndication` were **rejected** by the API.
  - `maxClinicalStage` values seen across baricitinib's 71 indication rows: `APPROVAL`, `PHASE_3`, `PHASE_2_3`, `PHASE_2`, `PHASE_1_2`, `PHASE_1`, `EARLY_PHASE_1`, `UNKNOWN`.
  - Source: introspection and queries run 24 Oct 2026 against the [Open Targets GraphQL endpoint](https://api.platform.opentargets.org/api/v4/graphql)

### Inferences: what to build, in priority order (all are my recommendations)

**A. Reuse or emulate**
1. **Evidence pack (must-have, copies `Observation`).** Every fetched fact becomes one item:
   ```json
   {"id": "E7", "source": "Open Targets|ChEMBL|PubChem|RCSB PDB|ClinicalTrials.gov",
    "kind": "target_disease_assoc|drug_mechanism|bioactivity|clinical_record|safety_warning|structure",
    "entities": {"drug": "CHEMBL…", "target": "ENSG…", "disease": "MONDO_…"},
    "data": {"...": "only the fields we need (compositional fetch)"},
    "url": "deep link to the record", "citation": "human-readable one-liner",
    "data_version": "OT 26.09 / ChEMBL release …", "retrieved_at": "ISO time"}
   ```
   Every juror sentence must end with an `[E#]` reference. A server-side validator rejects unknown IDs or sentences without a citation, re-asks once, and otherwise drops that juror, recording the reason. Display the **citation-validity rate** per run.
2. **Deterministic, templated queries.** The LLM never writes GraphQL or SQL. Use fixed Open Targets, ChEMBL and PubChem query templates whose only slots are IDs. Hard-code the filters (evidence types, score floors, which bioactivity types count). Cache every response in Postgres so the demo cannot be broken by a flaky API on stage. **Update any legacy Open Targets code to the 26.9.0 field names above**, and check other legacy fields (e.g. `knownDrugs`) by introspection before relying on them.
3. **Novelty labels** using `indications.rows.maxClinicalStage` for the query disease:
   - `APPROVAL` → "Approved for this disease"
   - `PHASE_3` or `PHASE_2_3` → "Late-stage trials for this disease (not a new idea)"
   - `EARLY_PHASE_1` to `PHASE_2` → "Already in clinical exploration"
   - `UNKNOWN` → "Clinical record, stage unclear"
   - no row for the disease → "Repurposing hypothesis"

   This one field stops the app from presenting multiple-myeloma standard-of-care drugs as "discoveries". Note that COVID-19 shows `PHASE_3` for baricitinib despite its 2022 FDA approval (§6), so treat `PHASE_3` and above as "known".
4. **Jury modelled on Discover Agent plus CRank:**
   - **Inputs:** 3–5 jurors, each given an *identical* evidence pack, with candidate order shuffled per juror (seed recorded) and temperature 0 or low.
   - **Structured output per juror:** rank, a 0–1 score, supporting and contradicting evidence IDs, an "insufficient evidence" flag, and a rationale of 40 words or fewer.
   - **Aggregation:** combine with **Borda or reciprocal-rank fusion**.
   - **Agreement statistics:** **Kendall's W** (overall), pairwise Kendall τ, and top-3 overlap.
   - **Contested candidates:** flag any candidate whose rank spread across jurors is large.
   - **Baseline juror:** add one **non-LLM** juror, e.g. a transparent score built from Open Targets target–disease association × ChEMBL potency × clinical stage elsewhere. This echoes the paper's heterogeneous ensemble and deterministic rules, and shows whether the LLMs add anything beyond the baseline.
5. **"For and against" pass** (copies "retrieves evidence supporting or contradicting"). For the top candidates, pull **safety** data (`drugWarnings`, `adverseEvents`) and **negative clinical signals** (terminated or withdrawn trials from ClinicalTrials.gov, fetching only the status, phase and condition fields). Show these next to the supporting evidence.
6. **A fixed DAG that users can see.** The pipeline is the plan: Resolve disease ID → targets → drugs on those targets → bioactivity and structures → novelty and safety → jury → user picks drug and structure → docking. Stream each node's status, time and LLM cost over server-sent events. A bounded plan, like the paper's fixed-size plan, guarantees predictable demo latency.
7. **Two-tier models.** Use a small, cheap model for extraction and formatting and larger models for the jury votes and the final student explanation. Show **cost and latency per run**, the way the paper reports cost per query.
8. **Feedback loop.** Thumbs up/down and comments per run go into Tiger Cloud Postgres together with the evidence pack, juror outputs and data versions, so any run can be replayed. An offline LLM-judge pass over stored runs (the paper's §3 practice) can be shown as a "quality dashboard".
9. **Explanations for students** (adapted from Figure 1 and the Glossary/Mapping agents):
   - Highlight entity chips that link out to Open Targets, ChEMBL and PDB pages.
   - Add numbered citations and a sources drawer with provenance labels.
   - Show an "ID resolution" first step (as in Figure 3's synonym question), e.g. "COVID-19 → MONDO_0100096".
   - Add a small **glossary** for terms such as pChEMBL, IC50, MONDO/EFO and clinical stage.
   - Show a capabilities and limitations notice and suggested follow-up questions.

**B. Juror prompt skeleton** (my wording; the paper publishes no prompts, but it advises "lean" instructions that rely "only on the obtained external information"):
> You are juror {k} of {n}. Rank ONLY the candidates listed, using ONLY evidence items E1…En below. Do not use outside knowledge, including any known clinical use of these drugs. For each candidate, return JSON with: rank, score (0–1), supporting_ids, contradicting_ids, insufficient_evidence (true/false), and a rationale of 40 words or fewer in which every sentence ends with [E#]. If the evidence cannot distinguish candidates, say so; do not guess.

**C. Evaluation protocol that fits in 24 hours** (keep it labelled "sanity and regression check", as the paper treats BioASQ):
1. **Known-answer check under three conditions.** Run COVID-19 with baricitinib and report baricitinib's rank in each:
   - (i) **open**: the full evidence pack;
   - (ii) **masked**: evidence linking any candidate to the query disease's clinical record removed (indications and trials for COVID-19 dropped);
   - (iii) **masked + blinded**: drug names replaced with "Drug A/B/C". Mechanism text may still give it away, so say so.

   The gap between (i) and (iii) is a visible, honest measure of how much the "answer" comes from leakage or memory rather than mechanism evidence. This is a "look-ahead bias removed" backtest that quant judges should recognise.
2. **Multiple myeloma.** Treat already-approved myeloma drugs (from `maxClinicalStage` = APPROVAL) as known positives. Report recall@10 with that evidence masked, and present the "no clinical record" candidates as hypotheses only.
3. **Mini regression set.** Take 10–20 disease → approved-drug pairs from Open Targets APPROVAL-stage indications, mask them, run the pipeline, and report recall@k. Rerun after each change, the way the paper uses BioASQ and STaRK.
4. **Report per run:** Kendall's W, citation-validity rate, juror abstentions, latency and cost.

**D. Docking framing (the paper has nothing on docking).**
- Present docking as a **structural-plausibility illustration**, never as evidence of efficacy.
- Add a **positive control**: dock the drug against its documented target. Open Targets lists baricitinib's mechanisms as "JAK1 inhibitor" and "JAK2 inhibitor". Then compare with the repurposing target.
- If a co-crystal structure exists in RCSB, re-dock into it and report pose RMSD; otherwise label the pose "unvalidated".

**E. What judges will probably find impressive** (my judgement, not sourced):
- "Evidence receipts", where every sentence is clickable through to a database record
- A live DAG with timings and costs
- A jury-disagreement heatmap with Kendall's W, plus the non-LLM baseline juror
- The open / masked / blinded baricitinib comparison
- Positive-control docking
- Replayable, version-stamped runs stored in Postgres

**F. Avoid** (each item is a lesson the paper states):
- LLM-written GraphQL, Cypher or SQL (non-determinism, timeouts)
- An embedding-based example router (high maintenance, "always yields a hit"); a fixed pipeline does not need routing
- Open-web search as jury evidence (non-credible sources, "tangential" grounding). If it is used at all, label it "web (unverified)" and keep it out of the jury pack
- Autonomous, open-ended LLM planning (unbounded time and cost)
- Benchmark-style headline accuracy claims (the "orthogonality" lesson)
- Treating raw citation counts, or impact-factor-weighted literature, as strength of evidence. The paper does blend citation and journal metrics into its literature ranking, but for students that should be shown separately, not used as a hidden weighting

### Gaps
- I did not research HRT, Snowflake, Tiger Data or Vultr prize criteria. Sponsor fit above is my inference.
- I did not verify Snowflake Cortex model availability or structured-output support, or DiffDock and Vina specifics; these are outside this paper.
- The Open Targets disease-side fields for "drugs for a disease" were not introspected; only `Drug` and its indication rows were checked.
- Whether a baricitinib co-crystal structure exists for JAK1 or JAK2 in the PDB was not checked.

## 6. What limitations or failure modes should shape the design and the pitch, and which claims can and can't the team make?

### Takeaway
The paper admits several weaknesses in a mature, well-funded system: **hallucinations persist**, it has **limited sensitivity to biological nuance** (gene paralogs), **web grounding can be tangential**, and **LLM-written graph queries and embedding routers are brittle**. It also reports **no accuracy numbers**. For the team specifically, the planned "known-answer check" is leaky through two channels:
- **Data:** ChEMBL and Open Targets already list **baricitinib → COVID-19 as a phase 3 indication**.
- **Model memory:** the baricitinib story has been public since February 2020, so LLMs are likely to know it.

The COVID-19 demo can therefore prove that the **pipeline works and its citations are honest**. It cannot prove **discovery**.

### Cited Findings
- **Limitations the paper states:**
  - "Important challenges remain. These include hallucinations and limited sensitivity to biological nuance, such as distinctions between closely related gene paralogs." — [Paper §5](https://arxiv.org/html/2608.12395v1#S5)
  - The Web Search Agent "can at times access sources that are not scientifically credible, including discussion forums and various blog posts". Grounded Gemini responses "can claim facts as grounded in specific web resources, while a closer inspection of those resources might show them only tangentially mentioning a related fact". Also: "Additional care and verification of sources is required". — [Paper §2.3.5](https://arxiv.org/html/2608.12395v1#S2.SS3.SSS5)
  - Mixing evidence of different confidence "can mislead the user in a question answering context". Generated queries can be "too complex and lead to timeouts". — [Paper §2.3.3](https://arxiv.org/html/2608.12395v1#S2.SS3.SSS3)
  - The embedding router "will always yield a hit, even if the query is not semantically related". — [Paper §2.4](https://arxiv.org/html/2608.12395v1#S2.SS4)
  - QA benchmarks are "orthogonal" to real user needs. — [Paper §3](https://arxiv.org/html/2608.12395v1#S3)
  - Research Assistant is "primarily designed to retrieve information about known relationships and established scientific facts"; prediction (the Discover Agent) is an extension. — [Paper §2.3.6](https://arxiv.org/html/2608.12395v1#S2.SS3.SSS6)
- **Baricitinib history.** BenevolentAI identified baricitinib as a potential COVID-19 drug, and "Benevolent's research findings were published in The Lancet in early February" 2020. Eli Lilly and NIAID then announced its "first large randomized trial in COVID-19 patients" (article dated 14 Apr 2020). — [TechCrunch, 14 Apr 2020](https://techcrunch.com/2020/04/14/potential-new-treatment-for-covid-19-uncovered-by-benevolentai-enters-trials)
- **Regulatory status.** The FDA approved Olumiant (baricitinib) in **May 2022** for certain hospitalised adults with COVID-19 (those on supplemental oxygen, non-invasive or invasive ventilation, or ECMO). The approval was based on the ACTT-2 and COV-BARRIER phase 3 trials. It had been available under an Emergency Use Authorization since November 2020. — [Lilly press release](https://investor.lilly.com/news-releases/news-release-details/fda-approves-lilly-and-incytes-olumiantr-baricitinib-treatment); [BioSpace syndication](https://www.biospace.com/fda-approves-lilly-and-incyte-s-olumiant-baricitinib-for-the-treatment-of-certain-hospitalized-patients-with-covid-19). A direct fetch of the Lilly page returned HTTP 403, so these details come from search-result summaries of these pages.
- **ChEMBL (live API, 24 Oct 2026).** Baricitinib is CHEMBL2105759 with max_phase 4.0. Its `drug_indication` records list **COVID-19 (MONDO:0100096; MeSH "Severe Acute Respiratory Syndrome") with `max_phase_for_ind` 3.0**, citing 17 ClinicalTrials.gov IDs (including NCT04401579 and NCT04421027). Baricitinib has 33 indication records in total. — [ChEMBL drug_indication API](https://www.ebi.ac.uk/chembl/api/data/drug_indication.json?molecule_chembl_id=CHEMBL2105759)
- **Open Targets (live API 26.9.0, data 26.09).** Baricitinib has `maximumClinicalStage` "APPROVAL" and mechanisms "Tyrosine-protein kinase JAK1 inhibitor" and "Tyrosine-protein kinase JAK2 inhibitor". It has **71 indications**, including **COVID-19 (MONDO_0100096) at PHASE_3**, acute respiratory distress syndrome at PHASE_3, pneumonia at PHASE_2_3, and COVID-19-associated MIS-C at PHASE_3. — [Open Targets GraphQL endpoint](https://api.platform.opentargets.org/api/v4/graphql)

### Inferences
- **Two leakage channels.**
  - **Data leakage:** if the pipeline pulls known drug–disease links or trials, baricitinib for COVID-19 is literally in the evidence.
  - **Model leakage:** the jurors' training data almost certainly includes the 2020–2022 baricitinib story.

  A top rank for baricitinib is therefore expected and is *not* validation. The masked and blinded protocol in §5C is the honest fix, and its result is itself an interesting demo moment.
- **Database lag as a teaching moment.** Both databases put COVID-19 at phase 3, although Lilly reports FDA approval in 2022. Show students that a database's "max stage" can trail regulatory reality, and stamp data versions on screen.
- **Correlated jurors.** LLMs share training data, so agreement between them is not independent confirmation. Pair the agreement statistic with the non-LLM baseline juror and the citation-validity rate, and never present "5/5 models agree" as evidence of truth.
- **Evidence-tier confusion** (the paper's causal-versus-expression point). Label evidence types: genetic association versus expression change versus literature co-mention versus measured bioactivity. Do not let one blended score hide them.
- **Graceful empty states.** Show "Insufficient evidence" rather than silently falling back to web search, as Figure 2's no-data loop does.
- **Claims guide for the demo and pitch:**

| Claim | OK to make? | Why |
|---|---|---|
| "Every statement links back to the database record it came from" | **Yes**, if the validator is enforced and the validity rate is shown | Same principle as the paper's Observation IDs |
| "Several independent LLMs ranked the same evidence; here is where they agree and disagree (Kendall's W = …)" | **Yes** | Describes what was measured, without claiming truth |
| "Our pipeline recovers a documented repurposing success (baricitinib, proposed in early 2020, FDA-approved for hospitalised COVID-19 in 2022)" | **Yes, as a sanity check** | Pipeline correctness only |
| "With indication evidence masked and names blinded, baricitinib ranked #k" | **Yes, only if actually run** | This is the honest discovery-style test |
| "Our AI discovered or predicted baricitinib" | **No** | The answer is in the data and probably in model memory |
| "Validated accuracy" or "X% accurate" from 1–2 examples, or citing the AZ paper for accuracy | **No** | The AZ paper itself reports no accuracy numbers |
| "Drug X will work for multiple myeloma" / "clinically actionable" | **No** | These are hypotheses for students to investigate |
| "The docking score proves binding or efficacy" | **No** | Present it as an illustrative pose, with a positive control |
| "Hallucination-free" | **No** | Even AZ's production system reports persistent hallucinations |
| "Like AstraZeneca's system" / implied endorsement | **Rephrase** | Say "design informed by lessons published by AstraZeneca's BIKG team (arXiv 2608.12395)" |

### Gaps
- I have no measured data on how strongly specific LLMs memorise the baricitinib–COVID-19 link. The masked and blinded protocol is my proposal and has not been tested.
- I did not record the ChEMBL release number, and the Open Targets data version (26.09) may change before the hackathon.
- The BenevolentAI mechanism hypothesis (reported as AAK1/endocytosis plus JAK inhibition) appeared only in a search-engine summary. The primary letter (Richardson et al., Lancet 2020) was blocked by a PMC reCAPTCHA, so verify it before using AAK1 as a docking target in the demo.
