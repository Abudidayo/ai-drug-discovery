# arXiv 2601.11560 ("DeepEvidence") and what it means for the OxHack '26 drug-repurposing app

## What exactly is this paper and what problem does it address?

### Takeaway
arXiv:2601.11560 is "DeepEvidence: Empowering Biomedical Discovery with Deep Knowledge Graph Research" by Zifeng Wang, Jimeng Sun and six co-authors (Keiji AI, UIUC, NIH/NLM, Weill Cornell, Osaka University, Kyoto University). It is v1 only, submitted 23 Dec 2025, and is a preprint that has not been peer-reviewed. It describes an LLM multi-agent "Deep Research" system that explores many biomedical knowledge graphs and APIs (including Open Targets, ChEMBL and PubChem), building an inspectable evidence graph as it goes. It is not a drug-repurposing ranking paper and not a docking or structure paper. Its relevance to the team is its evidence-handling pattern, its tools, its prompts and its evaluation design (good and bad).

## What is the pipeline/architecture, and which databases, models and tools does it use?

### Takeaway
An orchestrator agent (LangGraph state machine) writes a checklist plan and delegates to two sub-agents:
- Breadth-First ReSearch (BFRS), for wide, multi-database entity sweeps;
- Depth-First ReSearch (DFRS), for multi-hop drill-downs such as citation chains.

Every action is LLM-generated Python run in a Docker sandbox. Findings go into a deduplicated, provenance-tagged evidence graph that serves as memory. About 17 knowledge bases are wrapped as tools, including Open Targets (GraphQL), ChEMBL, PubChem, PubTator3, PubMed, ClinicalTrials.gov, KEGG, Reactome, UniProt and OpenFDA. Experiments used a single LLM, GPT-5, for every agent. There is no RCSB PDB tool, no docking or co-folding, no GNN and no model ensemble.

### Cited Findings
- **Architecture.** A hierarchical multi-agent design "implemented using LangGraph state machines".
  - The orchestrator "maintains a state machine that tracks search budgets, manages the evidence graph, and coordinates" BFRS and DFRS.
  - It invokes them "through tool calls that specify the search target (including entity names and standardized identifiers such as PubTator IDs or UMLS CUIs), the target knowledge bases, and the action budget". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **BFRS.** "issues broad, multi-graph queries to rapidly survey first-hop neighborhoods (e.g., identifying drugs linked to a disease across disease–drug or gene–disease graphs)". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **DFRS.** "builds on the important entities surfaced by BFRS and performs deeper, multi-hop exploration when the question requires multi-step reasoning or richer evidence discovery". The authors use "BFRS/DFRS" rather than BFS/DFS "because the proposed AI agents choose traversal steps autonomously rather than follow fixed graph-theoretic rules". Agents bridge graphs via shared "Bridge entities". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **Code as the action space.** "each tool generates executable Python code that is run within a sandboxed environment". The sandbox "tracks execution metrics (runtime and memory usage) and maintains persistent state across tool invocations". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **Evidence graph (methods).**
  - It stores "only high-value normalized biomedical entities such as genes, diseases, drugs, pathways, papers, and concrete findings", with canonical identifiers, deduplicated globally.
  - "every node and relation is grounded with explicit provenance from primary literature or curated knowledge graphs".
  - The agent "queries the existing graph before adding new content, merges near duplicates … and records conflicting findings with separate evidence links". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **"Memory Graph Protocol" prompt (Supplementary Note), concrete rules.**
  - Entity types: GENE/PROTEIN, DISEASE/PHENOTYPE, CHEMICAL/DRUG, CELL LINE/TISSUE, PATHWAY/GENE_SET, PAPER (PMID), FINDING.
  - Relation vocabulary:
    - mechanistic: ACTIVATES, INHIBITS, BINDS, PHOSPHORYLATES, REGULATES_EXPRESSION
    - membership: MEMBER_OF_PATHWAY, HAS_GENESET_MEMBER, EXPRESSED_IN
    - association: ASSOCIATED_WITH, CO_OCCURS
    - evidence level: SUPPORTS, REFUTES, INCONCLUSIVE_FOR, CITES
    - provenance: DERIVED_FROM_KG:<name@version>
  - Observations are "short factual sentences (<= 30 words)". "Prefer canonical CURIEs".
  - "Each merge cycle: <=10 new entities, <=16 new relations".
  - Conflicts: "Keep both relations with distinct evidence; tag with conflict_group:<id>".
  - "Every node and edge must include a provenance note (PMID or KG@version)". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **Orchestrator prompt.**
  - It requires a numbered checklist plan, updated after each step: "1. [v] First step (completed)", "[x] Second step (failed because...)".
  - It exposes `go_breadth_first_search`, `go_depth_first_search`, `code_exec_tool`, `add_to_graph` and `retrieve_from_graph`.
  - BFRS and DFRS sub-agents must return only "# Files saved" plus "Main findings: 1-2 short sentences", and "Keep the entire output under 10 lines total". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **Knowledge bases.**
  - The tool library covers "17 biomedical knowledge graphs and databases".
  - The KB paragraph names BioThings, ChEMBL, ClinicalTrials.gov, Gene Ontology, Human Phenotype Ontology, KEGG, NCBI Datasets API, OpenFDA, Open Genes, ProteinAtlas, PubChem, PubTator, PubMed, Reactome, UMLS and UniProt.
  - Open Targets Platform is described separately as a GraphQL API: "we constructed query templates with parameterized variables for target, disease, and drug searches". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **Tool design.** A two-layer design: a client class handles auth, rate limiting, errors and parsing, and tool functions return "a tuple of (DataFrame, formatted_output_string)" with an optional `save_path`. Unified tools merge sources concurrently: `search_drugs_unified` aggregates MyChem.info, OpenFDA, KEGG Drug, Open Targets and ChEMBL via ThreadPoolExecutor "with source attribution". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **Tools relevant to repurposing (Supplementary Table).**
  - Open Targets: `get_disease_associated_targets` ("with evidence scores"), `get_target_disease_evidence`, `analyze_association_evidence`, `get_drug_details` ("type clinical phase and linked entities").
  - ChEMBL: `get_target_bioactivities` ("IC50 Ki EC50"), `get_compounds_for_target` ("filtered by activity threshold"), `get_drug_mechanisms`, `get_drug_indications`, `search_drugs_by_indication` ("filtered by development phase"), and Tanimoto similarity and substructure search.
  - PubChem: `assess_drug_likeness` ("Lipinski and other rules"), `get_compound_bioactivities`, `get_safety_data`, `get_toxicity_info`.
  - PubTator3: relation search with predicates "TREAT CAUSE INTERACT INHIBIT ASSOCIATE", and typed boolean queries such as `@CHEMICAL_remdesivir AND @DISEASE_COVID_19`.
  - UniProt `get_protein_structure` returns only "Structural information and domain annotations". There is no RCSB PDB tool. — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **Models.** "For fairness, all agent systems, including DeepEvidence, were run with the same underlying LLM (GPT-5)." The LLM-only baselines were "GPT-5 and Sonnet-4.5" with "literature-search capabilities". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **Steerability.** "users can specify the biomedical domains relevant to a particular query, thereby constraining the search space, or provide expert priors". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **No structure or docking.** The discussion says the work "focuses mainly on text-based modalities, whereas we could further extend it to multimodal data such as imaging, structural biology, and proteomic information". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **Implementation knobs (legacy README).**
  - `DeepEvidenceAgent(model_name="gpt-5", api_type="openai"|"azure", ...)` and `agent.go(query, knowledge_bases=[...])`.
  - Budgets: `main_search_rounds_budget`, `main_action_rounds_budget`, `subagent_action_rounds_budget`.
  - "Dual Model Configuration" uses a cheaper model for BFS/DFS (example `gpt-4o-mini`). `light_mode=True` "Disables evidence graph".
  - Evidence-graph HTML export and token counters are included.
  - "DeepEvidence uses Docker for code execution". — [legacy DeepEvidence README](https://github.com/RyanWangZf/BioDSA/blob/main/legacy/biodsa/agents/deepevidence/README.md)
- **Legacy example script settings.** GPT-5 via Azure with `"reasoning_effort": "minimal"`, `"max_completion_tokens": 5000`, `subagent_action_rounds_budget=5`, `main_search_rounds_budget=2`, `main_action_rounds_budget=15`, `llm_timeout=120`. — [legacy run script](https://github.com/RyanWangZf/BioDSA/blob/main/legacy/scripts/run_deepevidence_agent.py)

### Inferences
- **"17" knowledge bases.** This is the 16 named KBs plus Open Targets. The paper's KB list omits Open Targets, but the supplementary table and methods include it.
- **Mapping to the team's pipeline:**
  - BFRS ≈ "disease → Open Targets associated targets → drugs linked to those targets" (a breadth sweep).
  - DFRS ≈ "for each shortlisted drug, drill into ChEMBL mechanism and bioactivity, PubChem properties and literature".
  - The evidence graph ≈ the team's Postgres experiment store.
  - The orchestrator ≈ a fixed, deterministic pipeline. A free-roaming agent is not needed.
- **Main lesson.** Tool and data structure, not model choice, is the main lever. GPT-5 alone scored 3.3% on HLE-Medicine (Figure 1e) versus 40.0% inside DeepEvidence. The team should invest first in a clean, ID-grounded evidence packet and only then in the LLM jury.
- **What is not in the paper.** Docking (DiffDock/Vina), RCSB PDB structures, the 3D viewer and the multi-LLM jury are all outside its scope. No claim in the pitch should lean on DeepEvidence for them.

### Gaps
- The paper does not report the GPT-5 settings used for the benchmark runs (reasoning effort, temperature, budgets). The legacy script's "minimal" reasoning effort may or may not match the reported runs.
- The paper does not describe how the agent picks among overlapping tools beyond prompt guidance, and has no ablation on this.

## How is it evaluated — datasets, splits, metrics, baselines — and what are the key quantitative results?

### Takeaway
The paper evaluates on two sets of tasks:
- Four adapted public benchmarks: HLE-Medicine (n=30), LabBench-LitQA2 (n=25), SuperGPQA clinical-medicine hard (n=172) and TrialPanorama-EvidenceQA (n=50).
- Seven newly curated tasks with n=14–25 each. The text says "six".

Metrics are multiple-choice accuracy, precision/recall/F1, gap-detection rate and recall@30. DeepEvidence (GPT-5) beats GPT-5, Sonnet-4.5, Biomni and ToolUniverse (the latter two also on GPT-5) on every task. However:
- Test sets are tiny and single-run.
- Most labels are generated by heuristics.
- There are no ablations, cost figures or significance tests.
- Text and figures disagree on some baseline numbers.

### Cited Findings
- **Open benchmark construction.**
  - HLE: subject "Medicine", image questions removed, "a total of 30 questions".
  - LabBench LitQA2: "randomly sample 25 questions".
  - SuperGPQA: difficulty "Hard" and field "Clinical Medicine", "172 questions".
  - TrialPanorama "EvidenceSummary": "retain the most recent 50 questions" and remove the study abstracts, "thereby requiring agents to actively explore the literature". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **Baselines.** "(1) two frontier LLMs (GPT-5 and Sonnet-4.5) equipped with literature-search capabilities, and (2) two general-purpose biomedical agents (Biomni and ToolUniverse)". All agents used GPT-5. — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **Headline results as stated in the text.**
  - HLE-Medicine: DeepEvidence "40.0%" vs "Biomni (20.0%), ToolUniverse (10.0%), Sonnet-4.5 (3.3%), and GPT-5 (3.3%)".
  - LabBench-LitQA2: "80.0%, more than doubling Biomni (32.0%) and surpassing Sonnet-4.5 (48.0%)".
  - SuperGPQA-Medicine-Hard: "47.1%" vs "Biomni 40.7%; Sonnet-4.5 43.6%".
  - TrialPanorama-EvidenceQA: "96.0%" vs "Biomni (84.0%) and Sonnet-4.5 (88.0%)". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **Figure 1e values (bar labels), which conflict with the text in places.**

  | Benchmark | Values in Figure 1e |

  | HLE-Medicine | DeepEvidence 40.0, Biomni 20.0, ToolUniverse 6.7, Sonnet-4.5 10.0, GPT-5 3.3 |
  | LabBench-LitQA2 | 80.0, 32.0, ToolUniverse 24.0, Sonnet-4.5 40.0, GPT-5 48.0 |
  | SuperGPQA | 47.1, 40.7, ToolUniverse 37.2, Sonnet-4.5 43.6, GPT-5 29.4 |

  — [Figure 1 (v1 HTML image)](https://arxiv.org/html/2601.11560v1/fig1.png)
- **Target identification (drug discovery).**
  - Construction: built from "85 human disease pathways" in KEGG KGML. "10 candidate options drawn from pathway members".
  - Ground truth comes from a "topological logic engine":
    - path polarity (genes with average polarity ">0.5" get "Gain 2 when targeted with an inhibitor");
    - betweenness centrality ("top 10%" with positive polarity get Gain 2);
    - "druggability filtering … via keyword matching against gene symbols".
  - Answers are "all Gain 2 options".
  - Result: DeepEvidence "68%" vs "Biomni at 56%, ToolUniverse at 40%, and general-purpose LLMs at 42%". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **Preclinical tasks.**
  - Mechanism-of-action / pathway reasoning (expert-curated MCQs with graded gain labels 2/1/0): "72%" vs "Biomni and ToolUniverse, both at 44%, as well as general-purpose LLMs at 52%".
  - In vivo metabolic flux (KEGG reaction graphs, 7 options): "80%" vs "Biomni at 68%, general-purpose LLMs at 60%, and ToolUniverse at 52%". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **Clinical trial development.**
  - Sample size estimation: the "25 most recent trials" from TrialPanorama, five options, with distractors made by "perturbation ratio in the range 0.25–4.00". Result "68%" vs "Biomni (20%), ToolUniverse (32%), and a PubMed-search LLM (24%)".
  - Drug regimen design: rule-based "Class I–IV" labels from an oncology dose-finding corpus. Result "52%" vs "Biomni (36%), ToolUniverse (28%), and PubMed-search LLMs (20%)".
  - Surrogate endpoint discovery: KEGG drugs "with approval dates in 2025", "bidirectional breadth-first traversal … (depth limit 10)", 6–10-option multi-answer MCQs. DeepEvidence "73.2% in precision, 75.0% in recall, and 73.3% in F1". Comparators:
    - Biomni 60.8 / 64.3 / 60.9
    - ToolUniverse 57.7 / 69.0 / 61.9
    - LLMs 58.4 / 61.9 / 58.7 — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **Evidence-based medicine (evidence-gap discovery).**
  - Built from "versioned Cochrane systematic reviews whose conclusions changed between consecutive updates".
  - Ground truth is "the set difference between the newer and older versions' included-study PMIDs".
  - Metrics: gap detection (at least one true positive in the top 30) and recall@30.
  - Gap detection: "90.0%, compared with 50.0% for Biomni, 15.0% for ToolUniverse, and 10.0% for PubMed-search LLMs".
  - Recall: "44.14%" vs "30.17%", "5.06%", "2.67%". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **Released test-set sizes (Hugging Face).** target_identification 25; moa_pathway_reasoning 25; in_vivo_metabolic_flux_response 25; sample_size_estimation 25; drug_regimen_design 25; surrogate_endpoint_discovery 14; evidence_gap_discovery 20. That is 7 configs and 159 items in total. — [HF datasets-server size API](https://datasets-server.huggingface.co/size?dataset=zifeng-ai/DeepEvidence)
- **Task count wording.** The text says "we curated six new benchmark tasks", but it describes seven. The project page says "7 task categories". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1); [BioDSA project page](https://biodsa.github.io/)
- **Per-gene results are single-run.** The per-gene supplementary heatmap states: "Results are descriptive, as each gene–method pair is evaluated once." Error bars appear in Figures 2b, 3b/d, 4c/e/g and 5d, but the captions do not say what they represent. — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1); [Supplementary target-ID heatmap](https://arxiv.org/html/2601.11560v1/supfig_target_identification.png); [Figure 4](https://arxiv.org/html/2601.11560v1/fig4.png)

### Inferences
- **What is not reported.** A search of the v1 source found no reporting of: API cost, tokens, latency, number of runs or seeds, temperature, variance, statistical tests, an ablation (for example of the evidence graph, BFRS/DFRS or light mode), a human-expert baseline, or contamination and leakage controls.
- **95% Wilson intervals (my calculation from the stated n; the paper gives none in the text):**

  | LabBench | 20/25 (61–91%) | GPT-5 12/25 (30–67%) |
  | SuperGPQA | 81/172 (40–55%) | Sonnet-4.5 75/172 (36–51%), a difference of 6 questions |
  | TrialPanorama | 48/50 (87–99%) | Sonnet-4.5 44/50 (76–94%) |

  Many pairwise gaps sit inside overlapping intervals. The large-effect results are the most credible: sample size, evidence gap, LabBench, and HLE against the LLM baselines.
- **Text/figure inconsistencies, suggesting a hurried preprint.**
  - The HLE baselines differ between text and figure (ToolUniverse 10.0 vs 6.7; Sonnet-4.5 3.3 vs 10.0).
  - On LabBench the text gives Sonnet-4.5 48.0, but the figure gives Sonnet-4.5 40.0 and GPT-5 48.0.
  - ToolUniverse's 73.7% on a 50-question set is not a multiple of 2%, so its denominator must differ (excluded failures?). This is undocumented.
  - The preclinical paragraphs cite Figure 5 for results shown in Figure 3.
  - The methods say "Humanity's Last Example".
- **Single-gene results (my tally from the per-gene supplementary heatmap; 35 targets, 46 gene-instances).**
  - 9 targets were answered correctly by all four methods, including plain LLMs: HbA1c, TGFB1, BDNF, HTT, SNCA, GBA, LRRK2, AMPK, DMD.
  - 9 were missed by all four: CTLA4, CASP1, TGFBR2, IRF5, KRAS, APC and three M. tuberculosis Rv genes.
  - At gene-instance level, DeepEvidence ≈ 29/46 vs Biomni ≈ 27/46, LLMs ≈ 22/46, ToolUniverse ≈ 18/46.
  - So the headline 68% vs 56% rests on a handful of items. The aggregation differs from the headline metric; this is a reading of the figure, not a reported number.
- **Labels are rule- or LLM-derived, not outcomes.** Target ID uses KEGG-topology heuristics, flux and surrogate tasks use templated KEGG traversal, and regimen classes come from rules. The released target-ID rows also contain hand-written clinical rationales, e.g. an HbA1c biomarker item whose KEGG field says "HbA1c is not a gene-encoded product", and a T2D item citing "clinical pharmacology evidence". This differs from the purely topological procedure in Methods. — [HF first-rows API, target_identification](https://datasets-server.huggingface.co/first-rows?dataset=zifeng-ai/DeepEvidence&config=target_identification&split=test)
- **Possible label noise.** The ulcerative colitis item labels TNF and IL6 as the gain-2 answers, with the rationale "validated therapeutic targets in Ulcerative Colitis". The IL-6 part is debatable for UC (not verified here). It shows how heuristic labels can encode judgement calls. — [HF first-rows API, target_identification](https://datasets-server.huggingface.co/first-rows?dataset=zifeng-ai/DeepEvidence&config=target_identification&split=test)
- **Baselines are not like-for-like.** DeepEvidence gets about 17 structured KBs plus a code sandbox. The "LLM" baselines get "literature search" only. The comparison shows the value of the whole system, not of any single design element.

### Gaps
- Per-item model outputs and traces are not released, so paired significance tests and independent re-scoring are impossible.
- The paper never says which model the "general-purpose LLMs" / "PubMed-search LLM" baseline was in the curated tasks (GPT-5, Sonnet-4.5 or an average).
- The four open-benchmark subsets (HLE, LabBench, SuperGPQA, TrialPanorama) are not in the HF dataset. Only the seven curated configs are listed. — [HF dataset API](https://huggingface.co/api/datasets/zifeng-ai/DeepEvidence)

## Is there public code, data or a hosted demo? How hard would it be to run or adapt within a few hours, and on what hardware?

### Takeaway
Code (MIT) and data (Apache-2.0 per the HF card) are public, and there are no model weights because the system calls API LLMs. However, the paper's code link now returns 404 after a September 2026 repository reorganisation:
- The paper-faithful implementation lives in an unmaintained `legacy/` tree that needs Docker and GPT-5-class API keys.
- The new "Harbor" package openly says it is not behaviour-equivalent to the paper.

There is no interactive hosted demo and no GPU requirement. Running the full agent at the hackathon is possible but a poor use of 24 hours. Porting a few tool patterns, the prompts and the small test set is the realistic path.

### Cited Findings

## Which specific ideas would most strengthen our app (evidence ranking, model jury, known-answer checks, docking, explanations)? What would judges find impressive?

### Takeaway
Emulate DeepEvidence's strongest, cheapest ideas:
- an ID-grounded, provenance-on-every-edge evidence graph;
- a "survey then drill down" (BFRS → DFRS) data flow, run as a fixed pipeline;
- a visible research log;
- a disciplined evaluation (same inputs for every model, graded labels, per-item heatmap).

Then add what the paper lacks: confidence intervals, leakage controls, and jury outputs that must cite evidence IDs. The paper's own data say the evidence pipeline matters more than which LLM is used, so build the evidence packet first. Treat the jury as an explanation and disagreement layer, and docking as an illustrative extra.

### Cited Findings (paper facts that motivate the recommendations)
- **Evidence graph transparency.** "the explicit construction of evidence graphs provides a transparent and traceable reasoning process in which intermediate entity relations and supporting evidence can be inspected and verified by humans". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **Target-identification workflow (Figure 2c).** "candidate search, broad evidence gathering, gene identity grounding across databases, evidence review and update, and comparative evaluation, progressively constructing and refining an evidence graph". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1); [Figure 2](https://arxiv.org/html/2601.11560v1/fig2.png)
- **Why generic agents fail.** "shallow exploration, issuing only a few searches before answering", plus "tool confusion" from "large tool suites". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **Evidence and tools mattered more than the model.**
  - In Figure 1e, GPT-5 with literature search scores 3.3% (HLE-Medicine) and 48.0% (LabBench). DeepEvidence on the same GPT-5 scores 40.0% and 80.0%.
  - Different LLMs given the same questions diverge widely, and which model is better varies by benchmark: SuperGPQA GPT-5 29.4% vs Sonnet-4.5 43.6%; LabBench GPT-5 48.0% vs Sonnet-4.5 40.0%. — [Figure 1 (v1 HTML image)](https://arxiv.org/html/2601.11560v1/fig1.png)
- **Graded labels.** The paper uses "gain equal to two, one, or zero" for correct, partially correct and distractor options. Partially correct options "incorporate valid biological or methodological elements but omit critical constraints". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **PubTator3 relation search** supports TREAT/INHIBIT/INTERACT predicates and typed queries like `@CHEMICAL_remdesivir AND @DISEASE_COVID_19`. — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **Origin of the baricitinib known answer.** Baricitinib for COVID-19 came from BenevolentAI's knowledge-graph-based repurposing in early 2020. The workflow combined "computational tools applied over an AI-enhanced biomedical knowledge graph" with human expertise. Press coverage reports about 90 minutes of compute plus about 3 days of human work, publication in The Lancet in February 2020, and an RCT start announced by Lilly in April 2020. — [Frontiers in Pharmacology 2021](https://www.frontiersin.org/journals/pharmacology/articles/10.3389/fphar.2021.709856/epub); [TechCrunch 2020](https://techcrunch.com/2020/04/14/potential-new-treatment-for-covid-19-uncovered-by-benevolentai-enters-trials)

### Inferences (recommendations: buildable in 24 hours, in priority order)
1. **Evidence graph in Tiger Cloud Postgres.** This is the core artefact and is also the Tiger Data angle.
   - Tables:
     - `entity(curie PK, type, label, source, source_release)`
     - `relation(id, subj_curie, predicate, obj_curie, evidence_ref, provenance 'OpenTargets@<release>' | 'ChEMBL@<version>' | 'PMID:…', observation ≤30 words, conflict_group)`
     - `run(run_id, disease_curie, params_json, model_ids, data_releases, started_at)`
     - `jury_vote(run_id, model_id, drug_curie, rank, score, cited_relation_ids[], rationale)`
   - Use the paper's predicate set (INHIBITS, BINDS, ASSOCIATED_WITH, SUPPORTS, REFUTES, DERIVED_FROM_KG) and its rules: CURIEs, deduplication, conflicts kept with `conflict_group`.
   - Build edges deterministically from API responses in code. Do not let an LLM write them, which avoids hallucinated edges.
   - Render a small interactive graph (disease → targets → drugs → papers) where every edge links to its source record.
2. **ID grounding chips.** Show and link MONDO/EFO (disease), Ensembl and UniProt (target), ChEMBL ID and PubChem CID (drug), PMID, and PDB ID (structure) on every card. The paper treats "gene identity grounding across databases" as an explicit step, and cross-database IDs are what make the app auditable.
3. **Deterministic BFRS → DFRS pipeline with budgets and caching.**
   - BFRS: Open Targets disease search → top-N associated targets with overall score and datatype breakdown → drugs acting on those targets, with phase and mechanism → filter to approved drugs.
   - DFRS, for each shortlisted drug: ChEMBL mechanism and pChEMBL/IC50 on that target, PubChem properties (Lipinski), and optionally PubTator3 TREAT-relation or co-mention counts.
   - Cap API calls per run and cache JSON snapshots for the live demo.
   - Show an orchestrator-style checklist log ("[v] 25 targets from Open Targets", "[ ] ChEMBL potency for 8 drugs"). It is cheap and makes the pipeline legible to students and judges.
4. **Transparent, deterministic evidence score; the jury is not the oracle.**
   - Rank with a simple, documented formula, for example a target–disease association score combined with a mechanism-direction match, potency and a clinical-phase flag.
   - Then give every Cortex model the identical evidence packet (the paper's same-input fairness principle), with a fixed prompt, temperature 0 where possible, and JSON output.
   - Require `cited_relation_ids` in every model answer. Mechanically reject or flag any claim citing an ID not in the packet.
   - Show agreement as a models × candidates heatmap, styled after the paper's per-item × method heatmap, plus top-k overlap or Kendall's W. Tag each candidate "consensus", "contested" or "single-model".
5. **Measured, not asserted, jury value.** Run each model twice: closed-book (no packet) and open-book (packet). Report how rankings and agreement change. If time allows, score each model and the jury's majority vote on the 25 DeepEvidence target-ID items, giving n and Wilson CIs. Treat the result as illustrative given the label caveats above.
6. **Two-mode known-answer check (COVID-19 / baricitinib).**
   - (a) Open-book "plumbing test": all evidence is allowed, so baricitinib should rank highly. Label it plainly as a sanity check.
   - (b) "Rediscovery under holdout": strip direct drug–disease evidence (Open Targets known-drug and clinical rows for COVID-19, ChEMBL indications for COVID-19, PubTator/literature co-mentions after about Feb 2020). Then check whether baricitinib still surfaces via its targets (JAK1/JAK2; AAK1 in the BenevolentAI rationale).
   - Report the result honestly either way.
   - For multiple myeloma, tag drugs already indicated for MM as "known/approved for this disease" so students can tell known answers from hypotheses.
7. **Student explanations.** For each candidate, show a "why this drug" path (disease → target with association evidence types → drug mechanism and potency → literature), written as ≤30-word observations with links, as the paper does. Add a "supporting vs refuting/conflicting" panel and a "partially supported" (gain-1-style) label for mechanistically plausible but weakly evidenced links. An optional "predict-then-reveal" quiz could reuse a few HF target-ID items, with label caveats noted.
8. **Docking as illustration only** (the paper has no structural component).
   - Ground the target to UniProt and pick a PDB entry for the same protein, ideally with a co-crystallised ligand in the relevant pocket.
   - Re-dock that native ligand as a positive control before docking the candidate.
   - Show the pose with a caveat. Never feed docking scores into the repurposing rank or call them affinities.
9. **What judges may find impressive (inference; no source on OxHack/HRT judging criteria).**
   - A live-growing evidence graph with click-through provenance.
   - The disagreement heatmap.
   - An honest evaluation slide (n, CIs, leakage control, closed- vs open-book).
   - Reproducible runs (model IDs, data release versions and parameters stored per run, mirroring the paper's `DERIVED_FROM_KG:<name@version>` idea).
   - A fast, cached demo path.
   - For a quantitative-trading sponsor such as HRT, rigour about uncertainty and evaluation is likely to land better than claims of discovery.
10. **Avoid:**
    - a free-roaming agent with dozens or hundreds of tools (the paper's own explanation for baseline failure);
    - an LLM code-execution sandbox (time and security cost);
    - KEGG/UMLS dependencies (keys and licence friction);
    - letting LLMs create graph edges or citations;
    - quoting DeepEvidence's accuracy numbers as if they describe the team's app.

### Gaps
- The paper provides no numeric ranking formula for drug candidates. Its prioritised lists are LLM-produced, so the team's scoring formula has no paper-based validation.
- No evidence was found, in this paper or its citing works, that multi-LLM juries or majority votes improve accuracy in biomedical evidence ranking. That would need separate research or the team's own measurement.
- Whether Open Targets and ChEMBL currently list baricitinib against COVID-19 (which would make the open-book check trivially "leaky") was not verified here.
- HRT, Snowflake, Tiger Data and Vultr judging criteria were out of scope and not researched.

## What limitations or failure modes (leakage, hallucination, contamination, overclaiming) should shape our design and pitch?

### Takeaway
The paper admits incomplete coverage, reliance on well-curated KGs, text-only scope and sub-expert performance. It does not address:
- tiny single-run test sets;
- heuristic labels;
- no ablations or costs;
- plausible answer leakage through live retrieval (later reviews and meta-analyses, trial registries);
- text–figure inconsistencies.

Independent 2026 work on other AI-science frameworks reports hallucinations, run-to-run variability and a large gap between benchmarks and real research. The team should pitch "transparent, evidence-linked hypothesis exploration for learning", with leakage-aware known-answer checks. It should not pitch discovery, validation, efficacy prediction or superiority.

### Cited Findings
- **The authors' stated limitations.**
  - "coverage is still incomplete, and the current benchmarks reflect only a subset of biomedical research tasks".
  - The system "currently works with well-curated knowledge graphs such as KEGG and Gene Ontology that offer stable schemas and high-quality APIs".
  - BFRS/DFRS "are unlikely to be optimal".
  - "DeepEvidence has not yet reached expert-level performance on many tasks".
  - The work "focuses mainly on text-based modalities". — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **The evidence-gap example harvested later syntheses.** Figure 5b says the agent was "searching recent systematic reviews (2015–2025), tracing cited RCTs". Its example evidence graph (Figure 5c) includes PMID 41239252 and PMID 40507374. PubMed identifies them as a BMC Cancer "Systematic Review"/"Network Meta-Analysis" (2025 Nov 14) and a Cancers (Basel) network meta-analysis (2025 Jun 5). — [Figure 5 (v1 HTML image)](https://arxiv.org/html/2601.11560v1/fig5.png); [PubMed esummary](https://eutils.ncbi.nlm.nih.gov/entrez/eutils/esummary.fcgi?db=pubmed&id=41239252,40507374&retmode=json)
- **Evidence-gap ground truth** is the set difference between Cochrane review versions. The dataset stores `new_review_doi`, e.g. `10.1002/14651858.CD000259.pub4`, and the agent had PubMed search and citation tools. — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1); [HF first-rows API](https://datasets-server.huggingface.co/first-rows?dataset=zifeng-ai/DeepEvidence&config=evidence_gap_discovery&split=test)
- **Sample-size items** come from TrialPanorama's "25 most recent trials". The tool library includes ClinicalTrials.gov `search_trials` and `fetch_trial_details` ("eligibility criteria outcomes and study design"). — [arXiv v1 HTML](https://arxiv.org/html/2601.11560v1)
- **Famous known answers are easy for plain LLMs.** In the per-gene heatmap, plain LLMs scored 100% on HTT, SNCA, LRRK2, GBA and DMD, matching all agents. — [Supplementary target-ID heatmap](https://arxiv.org/html/2601.11560v1/supfig_target_identification.png)
- **Independent evaluation of other frameworks** (Kosmos, K-Dense, ToolUniverse, BioAgents, AI Scientist-v2; not DeepEvidence) on published studies:
  - "real-world scientific tasks remain considerably harder than current benchmarks suggest";
  - "No AI framework matched the scope or depth of the original studies";
  - "severe hallucinations in final reports";
  - outputs varied between runs with the same prompt;
  - checking outputs needed substantial domain expertise. — [Sciety / bioRxiv 2026](https://sciety.org/articles/activity/10.64898/2026.06.24.734302)
- **DeepER-Med (2026).** This paper is from the NLM group that includes DeepEvidence co-author Zhiyong Lu. It argues that most deep-research systems "lack explicit and inspectable criteria for evidence appraisal". It does not mention DeepEvidence on its abstract page. — [arXiv 2604.15456](https://arxiv.org/abs/2604.15456)
- **The code authors model careful claims.** Their migration note insists the new package "must not be described as behavior-equivalent". — [MIGRATION.md](https://github.com/RyanWangZf/BioDSA/blob/main/agents/deepevidence/MIGRATION.md)

### Inferences
- **Leakage risks in the paper's evaluation (my reading; the paper does not discuss them).** With live PubMed and ClinicalTrials.gov access and no reported date cutoff:
  - evidence-gap answers can be partly harvested from newer third-party reviews or the updated review itself;
  - sample-size answers may be recoverable from the trial's registry record.
  So some reported gains may measure retrieval of existing syntheses rather than reasoning.
- **The same failure mode in the team's app.** In open-book mode, the baricitinib–COVID-19 link is probably in Open Targets/ChEMBL indications and in the literature (unverified). Every LLM has also likely memorised it since 2020. So "the jury agrees on baricitinib" mostly measures lookup and memorisation, not insight. Run the holdout mode before calling anything a "rediscovery".
- **Correlated errors.** LLMs trained on overlapping corpora can agree confidently and wrongly. Present agreement as "models concur given this evidence", not as a correctness signal. Show disagreement prominently.
- **Hallucination controls.**
  - Allow only evidence-ID-cited statements in the UI.
  - Validate IDs against the run's evidence tables.
  - Show "insufficient evidence" instead of free text.
  - Never let models generate PMIDs or ChEMBL IDs that the pipeline did not retrieve.
- **Small-n honesty.** Any team evaluation will be n ≈ 10–25. Always show n and a 95% interval, and avoid ranking models on differences of 1–3 items. The paper's own intervals overlap for several comparisons.
- **Claims the team CAN make (if implemented as above):**
  - "Ranks existing approved drugs using linked public evidence (Open Targets, ChEMBL, PubChem); every score traces to a source record."
  - "Shows where several LLMs agree or disagree when given identical evidence, and which evidence each one cited."
  - "Passes a known-answer sanity check (baricitinib for COVID-19) in open-book mode." Add the holdout result only if it was actually run, reported as observed.
  - "Docking shows one computationally predicted binding pose for illustration."
  - "Follows an evidence-graph design similar to recent research agents (DeepEvidence, Wang et al., arXiv:2601.11560), whose authors report that structured, provenance-tracked exploration beat generic agents on small biomedical benchmarks."
- **Claims the team CANNOT make:**
  - "discovers new treatments", "validated candidates" or "predicts efficacy/safety";
  - "the jury is more accurate than a single model" (unless measured, with CIs);
  - "no hallucinations";
  - "comprehensive evidence" (the paper concedes incomplete coverage even with about 17 KBs);
  - any DeepEvidence number (e.g. 68% target ID, 80% LabBench) presented as the app's performance. Those came from GPT-5 plus about 17 KBs plus a code sandbox, on n=14–172 multiple-choice sets.
  - docking scores as binding affinity or evidence of activity;
  - anything implying clinical use.
- **Suggested disclaimer.** "Educational research tool. Outputs are hypotheses generated from public databases and AI models, can be wrong or incomplete, and are not medical advice."

### Gaps

It was identified only via Semantic Scholar and not read. — [Semantic Scholar citations API](https://api.semanticscholar.org/graph/v1/paper/arXiv:2601.11560/citations?fields=title,year,venue,publicationDate,externalIds,authors&limit=100)
